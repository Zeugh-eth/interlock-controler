Robot arms that see, remember and interact.

Build a persistent object model around a closed-loop controller. Let AI choose goals and skills, while perception and measured outcomes keep the plan grounded.

Research: 22–23 October 2026 · SO-101 context · Primary repositories and documentation · No hardware operated

The recommendation for this arm

Extend the existing arm-agent runtime first. Add stable object identities, timestamped observations, explicit uncertainty and verified interaction outcomes. Use RoboEXP as the architectural reference; evaluate Grounded SAM 2 for perception, and borrow ConceptGraphs’ object-centric representation. Introduce a learned action policy after collecting reliable demonstrations.

This is an engineering recommendation derived from the sources below, not a tested integration or a claim that one repository solves the whole problem. “Best” here means useful for this arm and these capabilities, rather than a universal benchmark ranking.

Four capabilities that must stay distinct

Recognition and tracking

“This image region is a cup, and it corresponds to the cup in the previous frame.” Video masks and track IDs support this.

Object permanence

“The cup still exists behind the box.” Store its identity and last evidence, with increasing uncertainty about its current location.

Interaction state

“The cup is held by the gripper; the box is open.” Relationships and state transitions make memory actionable.

Predictive world model

“If I push here, what happens next?” Predict future state, video or actions. Predictions remain hypotheses until observations confirm them.

Best practices to carry into the implementation

  1. Separate deliberation from execution. AI selects “inspect”, “pick” or “place”; a local controller handles short corrections and joint constraints. MoveIt Servo documents this control layer; LeRobot documents asynchronous policy execution. Keep time-critical stopping independent of remote inference. Servo documentation · Async inference.
  2. Synchronize images with measured joints. Record capture time, camera pose, calibration version and actual joint state together. A moving wrist camera makes a delayed image geometrically misleading. Calibrate intrinsics and the camera-to-gripper transform; verify error across the working area. RoboEXP supplies wrist hand-eye calibration code. Calibration reference.
  3. Use a stable spatial frame. Express remembered positions in the arm-base or table frame. A pixel offset is useful for immediate visual servoing but cannot represent a location after the camera moves. Start with a calibrated table plane for tabletop targets; explicitly mark height/depth unknown when that assumption fails. ConceptGraphs provides the 3D representation reference.
  4. Persist identity, not certainty. Keep objects when occluded; store “last seen”, pose uncertainty, visibility and supporting evidence. Distinguish occluded, outside view, held and lost. Absence from one image is not evidence of removal. This proposed belief-state design extends the object-centric memory patterns above.
  5. Match instances across views. Combine appearance, geometry and plausible motion. “White cup” is a category, not an identity. Reacquire ambiguous targets from another viewpoint rather than merging them automatically. Grounded SAM 2 supplies tracking examples; durable identity requires an additional association layer.
  6. Predict → act briefly → observe → reconcile. After closing the gripper, do not declare “held” solely because the command completed. Combine available gripper feedback with visual evidence after a small lift. Confirm placement after release and retreat. POGS is a useful reference for updating manipulated-object state.
  7. Make inspection an action. If the object is hidden or confidence is low, change viewpoint before committing. Encode skill preconditions, expected effects, success checks and recovery paths. RoboEXP is the strongest architectural reference for exploration through interaction.
  8. Keep video queues bounded. Prefer fresh observations to a growing backlog. Timestamp and expire action proposals, discard results based on stale state, and tune action-chunk length against measured end-to-end latency. LeRobot's async design is a reference, not proof that any network delay is acceptable.
  9. Record failures as well as successes. Save raw images, observations, measured joints, requested and executed actions, outcomes, interventions and model/calibration versions. Separate simulated and physical episodes. Split evaluation by scene/session, not adjacent frames. LeRobot supplies the learning/data ecosystem; these evaluation rules are our proposed practice.
  10. Enforce motion authority in one place. One process owns the serial bus; concurrent skills must not compete. Bound motion and enforce stale-data handling locally. MoveIt’s checks illustrate useful controls, but depend on configuration and scene quality and are not a hardware safety guarantee.

A minimal architecture

Camera + joints → Detection / tracking → Object belief store → AI skill selection → Local controller → Arm

Feedback: every skill returns fresh observations and measured effects to the belief store. The planner receives compact state plus relevant images; a separate continuous perception path keeps memory updated between planner calls.

Minimum object record

object_id · label hypotheses · appearance features · pose_in_base · pose uncertainty · last_seen · visibility · relations · evidence references

Useful relations: on(cup, table), inside(part, box), held_by(box, gripper). Every relation needs an evidence time and confidence. Keep predicted effects separate from confirmed observations.

When a grasp is confirmed, propagate the object pose with the gripper transform while allowing for slip uncertainty. Once released, re-observe rather than retaining the carried pose as fact.

What this changes for our SO-101

The local README describes an existing single-owner runtime, skill loops and episode logging. The 22 October identification handoff records a real scan interrupted by a bus conflict, a visible green pad missed by the detector, and a cup not found. These are historical notes, not a check of the arm’s current state. The README’s older simulation-only statements do not establish the latest hardware validation status.

  1. First: trustworthy observations. Verify runtime ownership, frame freshness and capture-time pose. Resolve the green-pad detection path using saved images and record detector/runtime versions.
  2. Second: persistent object records. Map view-local detections onto stable IDs. Add a table-coordinate estimate and uncertainty; retain hidden objects without inventing precision.
  3. Third: explicit interaction outcomes. Make grasp, carry and release update relationships only after evidence checks. Add “inspect again” and bounded recovery behavior.
  4. Fourth: replay evaluation. Exercise occlusion, camera motion, duplicate objects and failed grasps on recorded sequences before physical evaluation.
  5. Fifth: learning. Validate LeRobot episode conversion, gather demonstrations and compare a small learned policy with the existing skills. Evaluate OpenPI or LingBot-VA only when the baseline and data pipeline are measurable.
