HackAIWoo · alternate pitch · for Seeed Studio

The SO-101 is open. We built the layer that makes it safe, visible and easy to use, and we are giving it back.

Seeed and the SO-ARM100/101 community opened the hardware. The next barrier to adoption is not the arm. It is what sits above it: who owns the serial port, what stops a model from crashing the arm into the table, how a newcomer sees what is happening, and how an AI agent drives it without guessing. We built that layer in a hackathon and propose to contribute it upstream.

The gap

Open hardware gets bought. Open infrastructure gets used.

A new SO-101 owner today meets four walls: scripts that each open the serial port and collide ("Port is in use"); no live view of load or temperature; an AI agent with no brakes; and every run lost because nothing recorded what happened. Each is solvable once, in the open, instead of by every user separately. That is the contribution.

What we contribute

Five pieces, one stack

Each card says what exists today and what we would hand over. The heat piece is the youngest and is labelled honestly.

1 · Daemon working

One owner for the bus, a documented API for everyone else

Today

  • Single process holds the serial port; torque is never dropped on start or exit.
  • 20 Hz state for every servo (position, goal, load, torque, temperature) over HTTP and WebSocket.
  • Camera proxy, annotated vision, demo recording, named poses. Binds to loopback only.
  • Wraps LeRobot rather than replacing it: a released holder hands the bus to lerobot-teleoperate and takes it back.
  • Full API.md a builder can code a client from.

We would upstream

  • The bus-ownership pattern and API spec as a reference for the SO-ARM100 repo.
  • The fake-bus test harness, so contributors can develop without an arm.
  • A LeRobot-compatible holder handoff, already in use.
2 · MCP working

Any model, open or closed, drives the same arm

Today

  • 31 tools: look, pose, align_to, grasp, release, stop, demo search and replay.
  • Every write returns one result: ok, frozen or refused, plus a plain-language reason. The model never has to guess what happened.
  • Grab logic is a decision tree with a stated attempt budget (three jaw closes, then ask).
  • A cheap model (Haiku) was used as the stress test; its failures drove the tool design.

We would upstream

  • The MCP server, as the first standard tool interface for the SO-101.
  • The driving-the-arm skill: when to look, grab, stop or ask.
  • The outcome vocabulary, reusable for other low-cost arms.
3 · Dashboard working

See the arm, take it back, stop it

Today

  • 3D model built from the real SO-101 STL meshes and URDF, driven by the same kinematics as the daemon.
  • Live gripper camera with a 1 cm table grid, detections and size/offset in cm.
  • Per-joint angle, load and temperature; sliders, nudges, named poses, big STOP, holder switch.
  • A log of every motion result from every client, human or agent.

We would upstream

  • The dashboard as a no-build, single-folder UI (vendored three.js).
  • The URDF-driven 3D viewer, usable by any SO-101 project.
4 · Heat performance analysis partly built

Make servo thermal behaviour visible, then measurable

Today

  • Temperature of each servo is read from the bus and shown live: servo colour on the 3D model runs 32 to 60 °C, and a joint is flagged hot at 55 °C or load above 85% of the guard.
  • The firmware alarm is 70 °C, so the display warns well before the servo trips itself.
  • Temperature is part of the API state, so any client can read it.

Not built yet (the contribution)

  • Temperature is not written to the command logs or demo files, so there is no thermal history to analyse.
  • Plan: log temperature and load per joint, report heat per task type (carry, hold, long reach), and publish a duty-cycle guide for SO-101 builds.
  • Plan: a temperature guard next to the load guard, so a hot servo slows or refuses before the firmware cuts out.
5 · Operational guardrails working

An AI that cannot hurt the arm, the table or the person

Today

  • Human first: the daemon starts with the human in control. Only a request carrying the human key can hand control to an agent. An agent cannot take it back.
  • STOP for anyone, resume for humans only. The legacy STOP file still works.
  • Load and lag guard on every move, always on; the arm freezes where it is and holds.
  • Table clearance check before the move, refused with the reachable height.
  • Joint limits clamp and report. One write at a time; extras are refused as busy.
  • Torque off while the arm is raised is refused without confirmation.

We would upstream

  • The guard set and the control model as a written safety profile for low-cost arms driven by AI.
  • The tests that prove each guard, including that the agent cannot override them.
Proof it is real

What a run looks like

On 22 to 23 Oct, Claude picked a carton and placed it on a tray through MCP on the real arm. Misses were analysed and fed back into the tool design: the grab now refuses to close the jaws when the object is not aligned, and reports not_aligned instead of failing silently. Twelve recorded runs are summarised in reports/robot-ai-practices/run-analysis.html.

The ask

Three things we want from Seeed

  1. A home. A place in the SO-ARM100/101 ecosystem (a repo under Seeed or a link from the docs) so owners find this layer on day one.
  2. Servo facts. Seeed's numbers on ST3215 thermal limits and duty cycle, so the heat guard uses vendor data rather than our guesses.
  3. Review. An engineer to check the guard set before we call it a safety profile.

In return: MIT-style licence, tests that run without hardware, and a maintainer for the first six months.

Talk track · about 4 minutes

Say it like this

30 s "You opened the arm. Thank you: we built on it in a day. What we hit next was not hardware. It was the layer above."

60 s "Four problems: port collisions, no visibility, an AI with no brakes, no memory of what happened. We solved them once. One daemon owns the bus. Everything else is a client."

60 s Live: open the dashboard, show the 3D model and temperature colours. Ask the agent to pick the carton. Hit STOP mid-move. "It froze where it was. The agent cannot take control back; only I can."

Appendix

Method and caveats

  • Figures come from the repo at commit 15d3a6d: 164 test functions across the daemon tests, 31 MCP tool names, 17 demo folders in the main checkout.
  • Heat: the colour ramp and 55 °C flag are in static/arm3d.js; temperature is polled about every 2.5 s (every 50th poll). No temperature appears in logs/20261023.jsonl, so no heat analysis exists yet. Do not present it as done.
  • The 70 °C firmware alarm is a comment in our code; confirm it against the ST3215 datasheet before quoting it to Seeed.
  • Guards are advisory in one case: table clearance depends on a model that is wrong when the arm rests on something.
  • "Licence" and "maintainer for six months" are offers to confirm with the team, not yet decided.
  • Vision uses YOLO-World and is imperfect for small objects above 6 cm; the pitch claims one successful carton pick and a documented set of failures.
