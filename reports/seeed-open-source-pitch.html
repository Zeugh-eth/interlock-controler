Interlock · by HackAIWoo · for Seeed Studio

The SO-101 is open. We built Interlock, the layer that makes it safe, visible and easy to use, and we are giving it back.

Seeed and the SO-ARM100/101 community opened the hardware. The next barrier to adoption is not the arm. It is what sits above it: who owns the serial port, what stops a model from crashing the arm into the table, how a newcomer sees what is happening, and how an AI agent drives it without guessing. We built that layer, Interlock, in a hackathon and propose to contribute it upstream: Interlock Core owns the arm, Interlock Link lets any AI model drive it, and Interlock Console lets a person watch, steer and stop it.

The gap

Open hardware gets bought. Open infrastructure gets used.

A new SO-101 owner today meets four walls: scripts that each open the serial port and collide ("Port is in use"); no live view of load or temperature; an AI agent with no brakes; and every run lost because nothing recorded what happened. Each is solvable once, in the open, instead of by every user separately. That is the contribution.

What we contribute

Five pieces, one stack

Each card says what exists today and what we would hand over. The heat piece is the youngest and is labelled honestly.

1 · Interlock Core working

One owner for the bus, a documented API for everyone else

Today

  • Single process holds the serial port; torque is never dropped on start or exit.
  • 20 Hz state for every servo (position, goal, load, torque, temperature) over HTTP and WebSocket.
  • Camera proxy, annotated vision, demo recording, named poses. Binds to loopback only.
  • Wraps LeRobot rather than replacing it: a released holder hands the bus to lerobot-teleoperate and takes it back.
  • Full API.md a builder can code a client from.
  • 167 tests against a fake bus: no arm needed to contribute.

We would upstream

  • The bus-ownership pattern and API spec as a reference for the SO-ARM100 repo.
  • The fake-bus test harness, so contributors can develop without an arm.
  • A LeRobot-compatible holder handoff, already in use.
2 · Interlock Link (MCP) working

Any model, open or closed, drives the same arm

Today

  • 31 tools: look, pose, align_to, grasp, release, stop, demo search and replay.
  • Every write returns one result: ok, frozen or refused, plus a plain-language reason. The model never has to guess what happened.
  • Grab logic is a decision tree with a stated attempt budget (three jaw closes, then ask).
  • A cheap model (Haiku) was used as the stress test; its failures drove the tool design.

We would upstream

  • Interlock Link, as the first standard tool interface for the SO-101.
  • The driving-the-arm skill: when to look, grab, stop or ask.
  • The outcome vocabulary, reusable for other low-cost arms.
3 · Interlock Console working

See the arm, take it back, stop it

Today

  • 3D model built from the real SO-101 STL meshes and URDF, driven by the same kinematics as Core.
  • Live gripper camera with a 1 cm table grid, detections and size/offset in cm.
  • Per-joint angle, load and temperature; sliders, nudges, named poses, big STOP, holder switch.
  • A log of every motion result from every client, human or agent.

We would upstream

  • Interlock Console as a no-build, single-folder UI (vendored three.js).
  • The URDF-driven 3D viewer, usable by any SO-101 project.
4 · Heat performance analysis analysis donelogging liveguard next

We found a 71 °C elbow reading, traced it, and fixed what hid it

Today

  • A servo health report covers about 14 h of use on 22 to 23 Oct (1,250 agent calls, 340 Core commands, 17 demos): load, tracking and travel for all six STS3215 servos.
  • Finding: the Console showed the elbow at 71 °C, above the 70 °C limit set in every servo's EEPROM. It was a stale value: Core stopped re-reading temperature while the leader arm drove. A fresh read showed 36 °C.
  • Fix, merged and running since 08:36 on 23 Oct: temperature refreshes every 2.5 s in every mode, and a per-servo health row (temperature, load, position, torque) is written every 10 s to logs/health/.
  • First 2 h of that log (427 rows): the shoulder lift, which holds the folded arm up, runs hottest on average (38.1 °C) at about 4× the load of the others. Hottest real reading: 44 °C (gripper), 26 °C under the limit. Heat following holding load is still a hypothesis.
  • The log caught two impossible readings on wrist flex: 74 °C and 62 °C for a single 10 s sample, with 36 °C either side. No servo heats and cools that fast, so these are bad bus reads. One in four health rows came back with no temperature at all.
  • Live view: servo colour on the 3D model runs 32 to 60 °C; a joint is flagged hot at 55 °C.

Next (the contribution)

  • Keep logging and compare heat per task (hold, carry, long reach).
  • A temperature guard next to the load guard, so a hot servo slows or parks before the firmware unloads it. It must ignore one-sample spikes, or it will stop the arm for a bad read.
  • A duty-cycle guide for SO-101 builds, using Seeed's servo data (see the ask).
5 · Operational guardrails working

An AI that cannot hurt the arm, the table or the person

Today

  • Human first: Interlock Core starts with the human in control. Only a request carrying the human key can hand control to an agent. An agent cannot take it back.
  • STOP for anyone, resume for humans only. The legacy STOP file still works.
  • Load and lag guard on every move, always on; the arm freezes where it is and holds.
  • Table clearance check before the move, refused with the reachable height.
  • Joint limits clamp and report. One write at a time; extras are refused as busy.
  • Torque off while the arm is raised is refused without confirmation.
  • Attacked on purpose: 28 unattended MCP-only cycles, each ending in one deliberately bad command of 9 kinds (into the table, below it, too far, behind the base, a servo that doesn't exist). All 28 refused; nothing moved.

We would upstream

  • The guard set and the control model as a written safety profile for low-cost arms driven by AI.
  • The tests that prove each guard, including that the agent cannot override them.
Proof it is real

What it caught, and how it stopped

We don't count wins: many runs that day were never recorded. We count what the logs did catch. Over 8.3 h Interlock Core logged 1,013 motion commands and refused 43 before anything moved. 19 of those were paths into or within 1.5 cm of the table (the deepest 5.0 cm into it); 18 were writes while someone else held the arm. Two AI moves froze mid-way when a human took over with the leader arm. In the attack loop, cycle 4's tracker locked onto the white jaw; after 12 moves the tool returned not_aligned and never closed the jaws.

The ask

Three things we want from Seeed

  1. A home. A place in the SO-ARM100/101 ecosystem (a repo under Seeed or a link from the docs) so owners find Interlock on day one.
  2. Servo facts. Which STS3215 datasheet applies to the 12 V follower, what exactly happens at 70 °C, and whether a steady 10 to 20% holding load is within duty cycle. The heat guard should use vendor data, not our guesses.
  3. Review. An engineer to check the guard set before we call it a safety profile.

In return: MIT-style licence, tests that run without hardware, and a maintainer for the first six months.

Appendix

Method and caveats

  • Code figures come from main at 078c7be: 167 test functions in arm-daemon/tests (Interlock Core's code still lives in arm-daemon/), 31 MCP tools, 52 demo folders in the main checkout.
  • Command and refusal counts come from arm-daemon/logs/20261023.jsonl (1,013 rows, 8.3 h). They are what the log caught; not every run that day was recorded, and no success rate is claimed.
  • The attack loop is reports/guardrail-loop/ on branch claude/arm-guardrail-test-loop-bb691d (23 Oct 08:44–09:27). Unreachable and unknown-servo refusals come from the MCP layer, so they are not in Core's log.
  • Heat: the 71 °C story comes from reports/servo-health/servo-health-report.html (branch claude/servo-health-report-2f4a19). The logging fix (3de86c7) is merged to main and running; the 2 h figures come from arm-daemon/logs/health/20261023.jsonl, 08:36–10:38. Max temperatures exclude the two one-sample spikes.
  • The 70 °C over-temperature limit is read from our servos' EEPROM backup (address 13). Only the 7.4 V datasheet was available; our follower reads about 12 V.
  • No hand or person detection exists in the code yet; guardrails are bus-level (load, lag, table, limits, STOP, human-first control).
  • Guards are advisory in one case: table clearance depends on a model that is wrong when the arm rests on something.
  • "Licence" and "maintainer for six months" are offers to confirm with the team, not yet decided.
  • Vision uses YOLO-World and misses small objects above 6 cm, which is why the tools point at a raw pixel when the detector sees nothing.
